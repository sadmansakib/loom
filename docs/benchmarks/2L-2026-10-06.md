# 2L — Context pruning (ADR-011) + long-context benchmark (2026-10-06)

Step 2L of `docs/plan-iteration-2.md`: implement the ADR-011
`PruningContextCompiler` and prove it on a long-context benchmark. B1's
final context (~27 K) sits well below the 64 K trigger, so a new task is
required to measure pruning at all. Commit `8e2530b`.

## Protocol

- **New task B5** (heavy — runs only when named in `LOOM_EVAL_TASKS`).
  Workspace `corpus/` holds 8 generated markdown files (`doc-01.md` …
  `doc-08.md`, ~40 KB each). The prompt processes them in ascending order,
  one tool call per turn: read a file, then append a line to it with
  `edit_file`. Tool set `ToolSet::ReadEdit` (`read_file` + `list_dir` +
  `edit_file`; no `search`) under `LONG_CONTEXT_SYSTEM_PROMPT`, which
  forbids search/sampling/partial reads and requires finishing all 8 files.
- No-prune arm: `LOOM_EVAL_TASKS=B5 LOOM_EVAL_RUNS=5 LOOM_EVAL_PRUNE=0` →
  `target/eval/report-B5-off.json`.
- Prune arm: `LOOM_EVAL_TASKS=B5 LOOM_EVAL_RUNS=5 LOOM_EVAL_PRUNE=1` →
  `target/eval/report-B5-on.json`.
- Model deepseek-flash, provider deepseek, price window off-peak.
- Gates before the run: `cargo test --workspace` **TBD passed / 0 failed /
  10 ignored**; `cargo clippy --workspace --all-targets` 0 warnings;
  `cargo fmt --check` clean.
- `PruneConfig` defaults: `trigger_tokens` 64,000, `min_reclaim_tokens`
  20,000, `protected_tail_tokens` 20,000, `protected_tail_turns` 3,
  `stale_error_turns` 4.

### Why this task

The task is deliberately **pruning-safe**: each read is made stale by the
edit that follows it, so once the file is written the old body is genuinely
disposable and the supersede strategy can drop it with no information loss.
An earlier B5 (read 16 files, list every heading at the end) was rejected
because it required retaining every body to the final answer, which is
adversarial to pruning: with pruning on the model re-reads pruned content,
turns rose (19–29), cache misses nearly doubled and cost rose ~80 %, with
one run hitting the 50-turn cap. A pruning benchmark must exercise content
that is actually redundant or superseded, not content the answer depends on.

## What changed

`PruningContextCompiler` (ADR-011) wraps `DefaultContextCompiler`; it
changes only the projection (the transcript is never mutated) and applies
four deterministic zero-model-call strategies in fixed order:

1. dedupe identical read-only calls (keep newest),
2. supersede reads of paths later modified by a tool effect,
3. drop stale errors older than `stale_error_turns`,
4. age out every read-only result outside the protected tail.

Each replacement is an informative stub that keeps `call_id`, so call /
result pairing stays intact and the model can re-run the tool. Protected:
the tail (≥ 20 K tokens *and* ≥ last 3 turns), user items, assistant text,
reasoning, and the task's first user item. Pruning fires only past the
absolute trigger (estimated input > 64 K) and only when reclaimable content
> 20 K; decisions are frozen in a `PruneCheckpoint` returned in
`CompiledContext` and passed back in `ContextInput`, so the projection is
byte-stable between checkpoints (one prefix-cache miss per trigger, never
per turn). Wired on by default in `loom-engine`, toggled in the harness by
`LOOM_EVAL_PRUNE`.

B5 ON final-turn `compiler_census.total` ≈ **35,737** (mean), dominated by
`tool_results` ≈ 32,200; `assistant_history` ≈ 1,545, `reasoning_replay`
300–1,628, `tool_specs` 479, `repo_facts` 250, `user_items` 226,
`system_prompt` 153. The projection is a bounded sawtooth (est tokens per
turn: 1,108 → 1,290 → 1,542 → 17,099 → … → 48,861 @t9 → **33,637 @t10** →

(t10, t14, t18), peaks ~50 K, troughs ~33–35 K. The pre-prune value would be
~64 K (≈ 50 K tail + one 15.5 K read), i.e. the trigger fires exactly when
the next read would cross it, and reclaims the superseded read.

Compared with OFF (monotonic to 127.6 K), the pruned projection stays under
36 K — a **−72 %** final context.

## Reading

- **Mechanism proven.** The `PruningContextCompiler` bounds the projection
  on a genuinely long task: final context **127.6 K → 35.7 K (−72 %)**, a
  bounded sawtooth that fires only when the next read would cross the 64 K
  trigger and reclaims the superseded read. Turns are identical (18.6) and
  all 10 live runs succeeded with 0 failed calls, so pruning does not cost
  task correctness here.
- **But it does not save money.** Billed input nearly halves (−47.6 %), yet
  **cost rises +24.6 %** and `cache_miss` tokens rise **+38.7 %**. Each
  checkpoint rewrites the prefix, so the live window (~35 K) is re-billed at
  cache-miss price; with ~4 checkpoints that is ≈ +40 K miss tokens. The
  no-prune arm is append-only, so its prefix is almost always a cache hit
  (hit rate ≈ 89 %) and the increments are its only misses (~104 K). Under a
  prefix-caching provider the removed cache-hit tokens are cheaper than the
  added cache-miss tokens, so the trade is net-negative on cost.
- **Disposition:** automatic pruning is therefore a **window-safety /
  bounded-latency** mechanism, not a cost optimization, in this
  configuration. This contradicts ADR-011's "pruning is free" premise and
  needs a decision: keep it as a safety valve (opt-in, or trigger set near
  the model's window so it fires only when the window is nearly full), or
  retune (larger `min_reclaim_tokens` → fewer checkpoints) and re-measure.
- **Aggregates only (V17).** N=5 per arm; the input, cost and cache-miss
  ranges are disjoint between arms (e.g. cost 0.01902–0.01936 vs
  0.02357–0.02435; cache_miss 103,392–104,120 vs 143,557–144,379), so the
  effect exceeds run-to-run spread. `output_tokens` (+14.6 %) is small and
  within noise. No invariant regression: schema↔parser agreement, replay
  equivalence and the closed-object spec tests all still hold.
- **Task-design caveat.** A long-context benchmark must exercise content
  that is genuinely disposable. The first B5 (read 16 files, list every
  heading) required retaining every body to the answer, so with pruning on
  the model re-read pruned content — more turns, cache storm, one 50-turn
  failure. The recorded task makes each read stale via a following edit.
